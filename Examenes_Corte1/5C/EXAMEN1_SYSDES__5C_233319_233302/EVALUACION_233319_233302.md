PREGUNTAS DE SEGUIMIENTO PARA DEFENSA
──────────────────────────────────────────────────────────────

1. [COMPRENSIÓN]
   Pregunta: Decidieron usar CURP como PK de CIUDADANO en lugar de un ID autoincremental. ¿Qué implicaciones tiene esto en términos de rendimiento de JOINs, ya que CURP es un VARCHAR de 18 caracteres comparado con un INTEGER?
   Respuesta esperada: Los JOINs con VARCHAR como FK son más lentos que con INTEGER porque las comparaciones de cadenas son más costosas. Sin embargo, para un sistema gubernamental donde el volumen de datos es moderado, el impacto es mínimo. La ventaja es que el CURP es un identificador natural único que elimina la necesidad de un mapeo adicional. Una alternativa sería usar ID autoincremental como PK y CURP como UNIQUE, obteniendo lo mejor de ambos mundos.

2. [FALENCIAS]
   Pregunta: Sus VIEWS solo están descritas conceptualmente pero no tienen SQL. ¿Podrían escribir aquí mismo el CREATE VIEW para "Solicitudes por ciudadano" incluyendo un HAVING que filtre solo ciudadanos con más de 2 solicitudes y un CASE que clasifique si son "frecuentes" o "esporádicos"?
   Respuesta esperada: CREATE VIEW vista_solicitudes_ciudadano AS SELECT c.Nombre, c.CURP, COUNT(*) AS Total_Solicitudes, CASE WHEN COUNT(*) > 5 THEN 'Frecuente' WHEN COUNT(*) > 2 THEN 'Moderado' ELSE 'Esporádico' END AS clasificación FROM CIUDADANO c JOIN SOLICITUD s ON c.CURP = s.CURP GROUP BY c.CURP, c.Nombre HAVING COUNT(*) > 2 ORDER BY Total_Solicitudes DESC;

3. [MEJORA]
   Pregunta: Su modelo no tiene un historial de cambios de estado de las solicitudes. Si una solicitud pasa de "Abierta" a "Aprobada" y luego a "Rechazada" por error, ¿cómo podrían rastrear quién hizo cada cambio y cuándo? ¿Qué tabla agregarían?
   Respuesta esperada: Agregaría una tabla HISTORIAL_SOLICITUD con: id PK, id_solicitud FK, estado_anterior, estado_nuevo, fecha_cambio TIMESTAMP, usuario_responsable VARCHAR. Cada vez que se actualiza el estado de una solicitud, se inserta un registro en esta tabla (idealmente con un TRIGGER AFTER UPDATE). Esto permite auditoría completa.

4. [DECISIÓN]
   Pregunta: En su tabla LICENCIA incluyeron CURP y ID_Tipo_Licencia como FK además de ID_Solicitud. Ustedes mismos mencionan que es "redundancia controlada y justificada". ¿En qué situación específica esta redundancia les ahorra un JOIN significativo?
   Respuesta esperada: Cuando se necesita un reporte rápido de "todas las licencias tipo B de un ciudadano específico", se puede consultar directamente la tabla LICENCIA sin necesidad de hacer JOIN con SOLICITUD para obtener el tipo de licencia o el CURP. En sistemas con millones de registros, evitar un JOIN puede ser significativo. Sin embargo, la desventaja es que si los datos no se mantienen sincronizados (un error en la aplicación), podría haber inconsistencia entre LICENCIA.CURP y SOLICITUD.CURP.

5. [APLICACIÓN]
   Pregunta: Su tabla EXAMEN_TEORICO tiene Calificación con CHECK entre 0 y 100, y un campo Resultado. ¿Qué pasa si un evaluador ingresa una calificación de 72 pero marca el resultado como "Reprobado"? ¿Cómo prevendrían esta inconsistencia a nivel de base de datos?
   Respuesta esperada: Se podría usar un CHECK constraint que valide la coherencia: CHECK ((Calificación >= Nota_Mínima_Aprobación AND Resultado = 'Aprobado') OR (Calificación < Nota_Mínima_Aprobación AND Resultado = 'Reprobado')). Alternativamente, se podría usar una columna generada (GENERATED ALWAYS AS) que calcule el resultado automáticamente basado en la calificación y la nota mínima, eliminando la posibilidad de error humano.
