PREGUNTAS DE SEGUIMIENTO PARA DEFENSA
──────────────────────────────────────────────────────────────

1. [COMPRENSIÓN]
   Pregunta: Implementaron herencia de tablas con Organizaciones como tabla padre y empresas_cliente/patrocinadores como tablas hijas. Si una organización es simultáneamente cliente y patrocinador, ¿cómo se refleja esto en su esquema y cómo lo consultarían?
   Respuesta esperada: La organización tendría un registro en la tabla organizaciones, un registro en empresas_cliente Y un registro en patrocinadores, ambos con el mismo id_organización como PK/FK. Para consultarlo se usa LEFT JOIN desde organizaciones hacia ambas tablas hijas, y con CASE se identifica el rol. Esto funciona porque la PK de las tablas hijas es simultáneamente FK a organizaciones.

2. [FALENCIAS]
   Pregunta: En su documento presentan 5 VIEWS pero no incluyen el código SQL de ninguna. Escriban en pseudocódigo la lógica de vw_asistencia_sesion, incluyendo cómo calcularían la tasa de asistencia y la clasificación de ocupación.
   Respuesta esperada: SELECT sesión, salón, cupo_máximo, COUNT(inscripciones) as inscritos, SUM(CASE WHEN asistió = true THEN 1 ELSE 0 END) as asistentes_reales, el porcentaje sería asistentes_reales * 100.0 / NULLIF(inscritos, 0), y la clasificación con CASE: >= cupo -> 'Lleno', >= 80% -> 'Alta', >= 50% -> 'Media', ELSE 'Baja'. GROUP BY sesión, salón, cupo. Se usa LEFT JOIN con inscripciones.

3. [MEJORA]
   Pregunta: Su trigger trg_validar_salon_evento verifica que el salón pertenezca al centro del evento. ¿Qué pasaría si no tuvieran este trigger y un usuario insertara una sesión con un salón de otro centro? ¿Cómo se manifestaría el error en los datos?
   Respuesta esperada: Sin el trigger, se podría programar una sesión del "Tech Summit en Polifórum Chiapas" usando un salón del "Centro de Convenciones San Cristóbal". Esto no violaría ninguna restricción FK (ambos IDs existen en sus tablas), pero sería lógicamente incorrecto. Los reportes de ocupación por centro serían erróneos, y la logística del evento sería imposible. Es un caso donde la integridad referencial no es suficiente para garantizar la lógica de negocio.

4. [DECISIÓN]
   Pregunta: Eligieron usar tablas catálogo (cat_tipos_sesion, cat_roles_ponente, etc.) en vez de CHECK constraints. Mencionen un escenario concreto donde esta decisión les ahorraría un ALTER TABLE que sería costoso en producción.
   Respuesta esperada: Si después de lanzar el sistema el cliente pide agregar un nuevo tipo de sesión como "Hackathon" o "Workshop", con CHECK habría que hacer ALTER TABLE sesiones DROP CONSTRAINT... ADD CONSTRAINT con el nuevo valor, lo cual en producción requiere bloquear la tabla. Con tabla catálogo, simplemente se hace INSERT INTO cat_tipos_sesion (nombre, descripcion) VALUES ('Hackathon', 'Sesión práctica competitiva'), sin tocar la estructura. En una tabla con millones de registros, el ALTER TABLE podría tomar minutos bloqueando la tabla.

5. [APLICACIÓN]
   Pregunta: Su esquema permite que un asistente se inscriba a sesiones que se solapan en horario. ¿Cómo agregarían una restricción (sin modificar el esquema) para prevenir esto?
   Respuesta esperada: Se implementaría un trigger BEFORE INSERT en inscripciones que, antes de insertar, verifique si el asistente ya tiene otra inscripción en una sesión cuyo rango de tiempo se solape con la sesión a la que intenta inscribirse. La consulta del trigger buscaría: SELECT 1 FROM inscripciones i JOIN sesiones s1 ON... JOIN sesiones s2 ON... WHERE i.id_asistente = NEW.id_asistente AND s1.fecha_hora_inicio < s2.fecha_hora_fin AND s1.fecha_hora_fin > s2.fecha_hora_inicio. Si encuentra registros, lanza una excepción.
